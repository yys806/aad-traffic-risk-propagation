## 二、这些数字推翻了什么、确认了什么

**确认（可以放心用）**：
1. 只要 vType 显式写干净，`setSpeed` 就是**完全服从**的——不需要改 SUMO 源码。
2. 积分器确实是 ballistic，且**跨零步也用梯形公式**，与纯 Python 侧一致。
3. 碰撞口径可控：`mingap-factor 0` 只认真实重叠，`collision.action warn` 不吞车。

**推翻（我们原来担心的）**：
- 「SUMO 会偷偷二次裁剪速度」——**不会**，前提是 vType 干净、speedMode=0。
- 「碰撞会被瞬移吞掉」——**不会**，前提是 `collision.action warn` + `time-to-teleport -1`。

**新发现（必须写进正式实验配置）**：
1. **`getLeader()` 返回的距离已扣掉 minGap**（95.0 → 93.0）。净距必须自己用 `getLanePosition` 算，
   否则会系统性少 2.0 m——这足以让 DRAC 算错。
2. **setSpeed 是粘性的**：任何一帧漏下发，该车就保持上次速度匀速跑。桥接代码必须有「每帧必发」的断言。
3. `DEFAULT_VEHTYPE` 不能直接用（有 speedDev、minGap 2.5、Krauss 插入安全检查）；
   必须显式定义干净 vType，否则车辆插入可能被拒或延迟。

## 三、Gemini 二审的判断（我采纳的部分）

它指出：**SUMO 在我们的架构里不跑 HDM，只是一个被 setSpeed 喂速度的积分器 + 坐标/碰撞容器**，
所以按「验证两个独立 HDM 实现等价」的标准写规格是打歪靶子；且 T0 已经覆盖 ballistic，
T1/T1b 是重复；容差应取机器精度（1e-9 量级）而不是拍 1e-3/1e-2。

**上面实测印证了这一点**：速度误差 0.0、位移误差 1.4e-14。**纸面上争论的 1e-2 容差根本用不上。**

## 四、修正后的最小验收协议（采纳 Gemini 的四测，去掉重复）

| 测 | 内容 | 通过线 |
|---|---|---|
| **A 运动学契约**（合并原 T0+T1b） | 单车：零速→冲过限速→−3 m/s²→跨零→恒零→再起步 | `|Δv| ≤ 1e-9`、`|Δx − 0.5(v0+v1)Δt| ≤ 1e-9`、跨零帧公式一致 |
| **B 净距与碰撞边界** | 两车开环：核对几何净距 vs `getLeader`；驶入 `0<gap<minGap`；驶入 `gap<0` | 全程 `teleported==[]`；只在 `gap<0` 报碰撞且车不消失 |
| **C 开环轨迹回放** | 把纯 Python 已跑好的 5 车 120 s 轨迹**开环**喂给 SUMO | 全车全帧 `|Δv| ≤ 1e-9`、`|Δx| ≤ 1e-7`、无异常消失 |
| **D 短闭环烟雾**（仅当下一步要在 SUMO 里加换道/多车道时才做） | 5 车 60 s，Python HDM 闭环接入 | 无噪声版前 10 步 `|Δx| ≤ 1e-9`；有噪声版关键指标一致 |

**关键洞察（Gemini 提的，我认同）**：先做 C 再做 D，能把「SUMO 引擎问题」和「我的桥接代码差一帧」分开。
C 过了而 D 偏了，一分钟就能断定是接线错。
