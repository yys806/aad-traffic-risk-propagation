## 一、这一模块要产出什么

一份**候选车名单**，每辆车一行：

| 字段 | 含义 |
|---|---|
| `veh_id` | 车辆 ID |
| `depart_planned` | 计划发车时刻 |
| `depart_actual` | 实际发车时刻 |
| `depart_delay` | 两者之差 |
| `t_i` | **该车跨越 3000 m 的仿真时刻**（决策时刻） |
| `lane` / `pos` / `speed` | t_i 时刻的车道、位置、速度 |
| `verdict` | 是否可用（到达终点 / 未到达 / 路线异常） |

**基线本身不改任何车的路线**——测量不干预。

---

## 二、实现要点（每一条都对应先前的坑）

1. **不用 `<flow>`，改用显式车辆清单**：这样每辆车的计划发车时刻可见、可重放。
   但按 GPT 的要求：**不能只用车辆总数证明背景等价**，必须按时段对账流量。
2. **不插探针**——名单从基线里的普通车中产生。这是 0.0.5c 的教训：
   30 m/s 插入需约 100 m 净空，在 1600 辆/时下根本插不进去。
3. **过线时刻用逐帧位置检测**（步长 0.1 s，30 m/s 下每步 3 m，
   跨线误差 ≤3 m ≈ 0.1 s），并与 `tripinfo.arrival` 对拍。

---

## 三、验收（跑之前写死）

| 项目 | 标准 |
|---|---|
| 车辆总数对账 | 生成数 = 计划数；`Inserted` 与生成数之差 ≤ 1% |
| **按时段流量** | 每 60 s 的实际入口车辆数，与计划值偏差 ≤10% |
| **departDelay 分布** | 报告中位数与 p90；若 p90 > 30 s，说明入口通行受限，需说明 |
| 过线时刻 | 单车空路时，从 2900 m 出发到跨 3000 m 应为 **3.33 s**（100 m ÷ 30 m/s） |
| 到达对账 | 已过线车中，`到达 + 未到达 + 异常 = 过线总数` |
| 跨线误差 | 过线时刻与 `tripinfo` 推算值之差 ≤ 0.2 s |

## 四、预测（R08 第 3 条）

| 量 | 预测 | 依据 |
|---|---|---|
| 660 s、1600 辆/时 → 计划车数 | 1600 × 660 / 3600 ≈ **293 辆** | 流量定义 |
| 过线（跨 3000 m）的车数 | 约 **250–290 辆** | 除去末尾未到岔口的 |
| 到达终点的车数 | 约 **200–260 辆** | 再除去末尾未到终点的 |
| 单车 2900 m → 3000 m 用时 | **3.33 s** | 100 / 30 |
| departDelay 中位数 | **< 10 s** | 1600 辆/时下入口应有空隙 |

**超出这些范围先查 bug。**
