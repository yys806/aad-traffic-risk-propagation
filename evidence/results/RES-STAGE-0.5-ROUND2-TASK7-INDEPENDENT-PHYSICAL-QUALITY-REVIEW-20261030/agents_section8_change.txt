+### A. 风险分级验证
+
+所有任务开始验证前，先形成简短的影响范围判断：
+
+- 修改了哪些文件。
+- 涉及哪些模块和数据接口。
+- 是否改变正式科研逻辑。
+- 哪些测试真正能够覆盖本次变化。
+
+按照最小充分验证原则执行。
+
+### B. 按任务类型选择验证
+
+**纯文档或索引任务：**
+
+- 修改文档时运行 `validate_project_docs.py --strict-git`。
+- 只有修改结果注册、manifest、audit 或证据索引时才运行对应 evidence exporter 验证。
+- 不默认运行全量 pytest。
+- 不运行全仓库 compileall。
+
+**独立离线分析脚本任务：**
+
+- 运行新增或修改部分的定向测试。
+- 运行直接依赖模块的必要测试。
+- 对修改的 Python 文件进行必要语法检查。
+- 不默认运行全量 pytest。
+- 不默认对整个 code/src、code/scripts、code/tests 运行 compileall。
+
+**共享核心模块或生产科研逻辑任务：**
+
+涉及正式测量、身份、数据流、evaluation、共享接口、Gate、实验执行守卫等模块时：
+
+- 先运行定向测试。
+- 根据实际影响决定是否扩大回归。
+- 对跨模块或高风险修改，允许运行全量 pytest。
+- 需要时执行 compileall。
+- 记录验证覆盖范围和剩余风险。
+
+全量 pytest 不再是所有任务的默认收尾动作。
+
+### C. 全量测试的准入条件
+
+只有以下情况才默认考虑全量测试：
+
+1. 修改共享核心接口或公共数据契约。
+2. 修改正式测量、身份或事件提取实现。
+3. 大范围重构或影响多个模块。
+4. 修改项目级执行守卫或实验安全机制。
+5. 研究者明确要求全量验证。
+
+如果本次改动影响范围有限，定向测试已经充分覆盖，不应为了追求测试数量而额外执行全量测试。
+
+### D. 历史失败处理
+
+测试失败分为三类：
+
+- 本任务引入的失败：必须处理。
+- 本任务直接依赖且阻断交付的历史问题：先报告，必要时进行最小范围修复。
+- 与本任务无关的历史失败：记录原因、影响和证据，不自动修复。
+
+禁止为了让全量测试变绿而：
+
+- 修改无关历史测试。
+- 恢复大量无关历史输入。
+- 修复与本任务无关的 Git 换行问题。
+- 扩展为历史工程清理任务。
+
+环境问题只允许进行一次有明确依据的有限排查。仍无法解决时，记录并停止扩展。
+
+### E. 验证时间预算
+
+一般离线分析和文档任务：
+
+- 工程验证时间原则上不超过任务总投入的 20%。
+- 通常不超过 30 分钟。
+- 达到任一边界后，如果仍存在与本任务无关的验证问题，立即停止并报告。
+
+涉及正式测量、身份、核心接口、Gate 或安全机制的高风险修改不受上述时间上限限制，但必须说明额外验证的必要性。
+
+科研数据分析和必要的科研计算不计入工程验证时间。
+
+### F. 纯 Git 检出验证
+
+仅在以下情况有必要时执行：
+
+- 新增便携证据入口。
+- 修改证据打包或导出机制。
+- 修改 `.gitattributes`。
+- 修改依赖文件字节保真或跨平台检出行为。
+
+不要求每个纯离线分析任务都重复执行全套纯 Git 克隆验证。
+
+### G. 提交与推送
+
+- 每个独立有效任务使用清晰的 Conventional Commit。
+- 验证满足本任务实际风险要求后，正常 commit 和 push。
+- 推送后核对远端 HEAD。
+- 不推送未完成或验证失败的科研产物。
+- 保留原始失败记录，不得伪装成首次通过。
+
+默认在 `main` 上处理普通任务；高风险验证可用临时分支。合理完成并验证后自动执行 `git commit` 与 `git push`，无需重复确认。命令成功只证明其覆盖范围。
 
 不得执行可能丢失资料的 `git clean`、`git reset --hard`、批量 checkout、递归删除或覆盖。确需清理时先精确解析目标，优先使用可恢复操作，并严格限制在已授权范围内。
